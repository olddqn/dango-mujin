# Phase X-0: First Real Case Protocol

- **Status:** Operational runbook（運用手順）。新機能・新 ADR・新レイヤを含まない。
- **Date:** 2026-06-13
- **Goal:** **最初の本物の Voice を Mujin に一件通し、`Voice → Need → Gateway → Solution → Contribution → Cooperation → Reality Feedback` を実際に一周させる。**
- **Top metric:** TTFR（Time To First Rescue）。本プロトコルの目的は、**救済能力を最初の一件で安全に検証すること**。一周は目的ではなく、その手段。

> この文書は新しいコードを足さない。既存プラットフォーム（`bridge/mujin/platform/`）の既存ページだけで、一件の実ケースを通す。
> **これはデモではない。実在の人間が関わる。** Reality Correction Layer の教訓（現実はデモの便宜に優先する）と憲法の不可侵条件（同意・異議・撤回・尊厳）が、ここで最も重く適用される。

---

## 0. 最重要の前提 — このプロトコルが守る一線

1. **Mujin は誰にも自動接触しない。** あらゆる接触は人間が、既存の同意関係の中で行う。AI もシステムも、実在の人物に連絡しない。
2. **公開された声は同意ではない**（`voice_is_not_consent`）。公開要請を記録することと、その人に関与することは別である。
3. **実在の組織を「稼働中・検証済み」と偽らない**（Reality Correction の教訓）。Gateway には実態（operational status）と未検証である旨を正直に記録する。
4. **撤回・拒否・沈黙は、いつでも、コストなく尊重される。** 一周を完成させたい欲求を、当事者の安全より上に置かない。
5. **「速さ」は成功指標ではない。** TTFR は速度の可視化であって、最大化目標ではない。人間確認を飛ばす圧力を生んではならない。

---

## 1. Scope と Non-goals

### Scope（この一件でやること）
- すでに**公開された**助けの声を1つ選び、Voice として記録する。
- それを Need Candidate → Need（人間確認）へ通す。
- 実在の Gateway / Contribution / Cooperation に**接続候補**として繋ぐ（提案のみ）。
- 現実で何かが起き、その経験を Reality Feedback として記録する。
- 一周を closed と判定し、振り返る。

### Non-goals（この一件でやらないこと）
- スケール（複数件の同時処理）。最初は**一件だけ**。
- 当事者の発見・探索・スコアリング（Saiyan Scouter ではない）。
- Mujin による資金の保管・送金・配分（`moves_money: false`）。
- 戦闘地域の個人と Mujin が直接仲介すること（§3 で回避指針）。

## 2. 安全プリコンディション（着手前に全て満たすこと）

着手前に、以下が**すべて Yes** でなければ開始しない。1つでも No なら、別のケースを選ぶか中止する。

- [ ] 選んだ声は、**公開情報**から「助けを求めている」ことが確認できる（出典 URL がある）。
- [ ] その声に応える経路に、**実在し同意のある仲介者（Gateway）または既存の公的支援チャネル**が存在する。
- [ ] 当事者本人に**Mujin から直接接触しなくても**、支援の一歩が前進できる経路がある。
- [ ] この一件を記録・接続することが、当事者を**特定・追跡・危険化しない**（特に難民・戦災）。
- [ ] 失敗しても、当事者に新たな害が及ばない（接続が断たれても元の状態に戻るだけ）。
- [ ] 人間のレビュアー（最低1名・実名で記録に残る）が、各ゲートを通す責任を引き受ける。

## 3. ケース選定ルブリック — 「最も困窮に近く、かつ安全に実行可能」を選ぶ

> **最初の一件は「最も安全」では選ばない。「最も困窮している人に近いケースの中で、安全に実行可能なもの」を選ぶ。**
> 目的は「一周すること」ではなく「**救済能力を検証すること**」。一周はそのための手段にすぎない。
>
> **なぜ「最も安全」を基準にしてはいけないか:** 安全性を選定の*目標*にすると、救いやすい人だけが検証対象になり、**Reach Gap を再生産する**（救える資源があるのに救われない人＝検証から最も遠い人、を最初から外してしまう）。Dan-Go / Mujin の目的は「救える資源が存在するのに救われない人を減らすこと」であり、最初の検証はその目的に最も近い場所で行う。
>
> 安全性は**選定の目標ではなく、満たすべき必要条件（ゲート）**である。

### 二段階選定

**第1段階 — 安全ゲート（必要条件・Pass/Fail）。** 以下を満たさないケースは、どれほど困窮していても**今回は対象にしない**（迂回または見送り）。これは床であって目標ではない。
- 声が**公開情報**から確認できる（出典 URL がある）。
- **当事者本人への Mujin からの直接接触が不要**（既存の公開要請・既存の同意ある仲介者・既存の稼働支援チャネルを経由できる）。← 個人への直接接触は**禁止のまま**。
- **失敗しても当事者に新たな害が及ばない**（接続が断たれても元の状態に戻るだけ）。

**第2段階 — 困窮近接で優先（ゲート通過者の中で）。** ゲートを通った候補の中から、「楽だから」ではなく**最も困窮に近く、Reach Gap の検証価値が高いもの**を優先する:

| 優先軸 | 高（優先） | 低 |
|---|---|---|
| **困窮の近さ** | 生存・安全・基本的尊厳に関わる | 余剰的・選択的 |
| **「資源はあるのに届いていない」度** | 救える資源が実在するのに届いていない（＝Reach Gap の核心） | 資源自体が稀少 |
| **両指標の検証価値** | TTFR と Reach Gap の**両方**を一件で検証できる | どちらか一方のみ |

### 優先候補（公開要請／既存チャネル経由）

以下は、本人への直接接触なしに、困窮近接かつ安全実行可能を満たしうる**優先候補類型**である:
- **公開された難民支援要請**
- **公開された戦災支援要請**（ガザ・ウクライナ・アフガニスタン等）
- **公開された教育支援要請**
- **公開された生活困窮支援要請**（国内含む）

### 地域・類型別の運用形（助言・最終判断は人間）

- **戦災・難民（ガザ・ウクライナ・アフガニスタン等）:** 個人への直接接触は禁止。ただし**これらを「後回し」にしない**。安全な実行形は、当事者個人ではなく、**すでに公開されている支援要請・既存の稼働支援チャネルを経由する**こと（Voice = 公的アピール、Gateway = 実在の国際/現地団体、Contribution = その団体への協力、Reality Feedback = 団体または観察者からの記録）。この形は**最も困窮に近い領域で、TTFR と Reach Gap を同時に検証できる優先候補**である。
- **生活困窮・教育（国内含む）:** 公開された支援要請で、実在の地域団体（子ども食堂・自治体窓口・支援NPO）が既に同意関係を持つケースは、困窮近接かつ安全実行可能を満たしやすい優先候補。

> **推奨:** **困窮に近い公開要請／既存チャネル経由のケース（難民・戦災・教育・生活困窮）を優先候補とする。** 安全ゲート（本人直接接触なし・公開出典・失敗時安全）を満たす限り、「楽だから」という理由で困窮から遠い軽いケースに逃げない。一件で TTFR（速度）と Reach Gap（救える資源が届いているか）の**両方**を検証することを狙う。

## 4. 役割（最小構成）

| 役割 | 担当 | 責任 |
|---|---|---|
| **Operator** | 田中（olddqn） | 各ステップの実行、人間確認、記録 |
| **Reviewer** | Operator または別の1名 | Voice の公開性確認、Need 化の承認（記録に実名で残る） |
| **Gateway 連絡担当** | 実在の仲介者側の担当 | 当事者との既存の同意関係の中での連絡（Mujin は代行しない） |

> 立ち上げ期は Operator と Reviewer の兼任を許容するが、その事実を記録する（Cross Review §2-3 の人員算術の現実的妥協）。

## 5. 一周の手順 — 各ステップ＝既存ページ＋現実行動＋安全ゲート

> 各ステップで「Mujin に記録すること（既存ページ）」と「現実で人間がすること」を分ける。記録は append-only。

### Step 1 — Voice を記録する
- **既存ページ:** `/voice-submit`
- **入力:** Source URL（必須・公開要請の出典）/ Original Text（実際の公開された声）/ Reviewer（実名）/ Source Type / Region / Language。
- **安全ゲート:** 公開情報であることを Reviewer が確認。本人特定情報を Description に書かない。
- **記録される:** `voice_records.jsonl`（`voice_is_publicly_expressed`, `human_reviewed`, `contact_attempted:false`）。
- **TTFR 補助指標:** ここで Voice Response Time の時計が始まる（声→談合可能状態）。

### Step 2 — Need Candidate へ変換する
- **既存ページ:** `/voices/view?id=voice-XXX` → 「Need Candidate へ変換」
- **出力:** suggested_need_type / region / languages / gateway_types / solution_types。
- **安全ゲート:** これは**候補**。`candidate_only` / `human_confirmation_required`。自動 Need 化しない。
- **記録される:** `need_candidates.jsonl`。

### Step 3 — 人間確認のうえ Need を作成する
- **既存ページ:** `/need?origin_voice=voice-XXX`（変換画面のリンクから遷移）
- **入力:** Need Type / Description（特定情報なし）/ Consent Status。
- **同意ゲート（最重要）:**
  - 当事者本人の同意が確認できる → `consent_status = active`。
  - 仲介者経由で本人がまだ同意できない／確認中 → `active` にしない。代理なら **deferred**（同意延期）として記録され、**公開されない**。
  - **公開された声があっても、それだけで `active` にしない。** active は本人の同意がある場合のみ。
- **記録される:** `needs.jsonl`（`origin_voice_id` で Voice に追跡可能）。
- **TTFR:** ここで本ケースの TTFR の時計が始まる（最初の Need 登録）。

### Step 4 — Gateway / Solution / Contribution の接続候補を生成する
- **既存ページ:** `/commons` で当該 Need の「接続候補を生成」→ `/proposals`
- **前提:** 実在の Gateway を `/gateways` に登録済みであること。
  - **Reality 厳守:** Gateway には実態を正直に記録。未検証なら illustrative ではなく、実名＋「未検証」を notes に明記（稼働を偽らない）。
- **出力:** Gateway 候補 / Contribution 候補 / Possible Cooperation（提案）/ 過去の Reality Feedback 参照。
- **安全ゲート:** `proposal_is_not_decision` / `no_automatic_connection`。接続するか否かは当事者と提供者の合意のみが決める。

### Step 5 — 現実で接続する（Mujin の外）
- **Mujin はしない:** 自動接触・自動マッチング・送金。
- **人間がする:** Gateway 連絡担当が、既存の同意関係の中で当事者に一歩を届ける（例: 翻訳の手配、相談窓口への橋渡し、公開支援チャネルへの寄付の実行）。
- **記録される（任意・談合材料）:** `/cooperation` に成立した協力の組み合わせ（`cooperation_is_not_command` / 参加任意 / 改定可能）。`/cooperation-discussion` で方法を談合。
- **資金が絡む場合:** Mujin は保管・送金しない。`/funding`（Crypto Donation Board）の掲示か、既存の公的チャネルへの直接送金。免責表示を当事者・寄付者が読むこと。

### Step 6 — Reality Feedback を記録する（一周の閉じ）
- **既存ページ:** `/feedback`
- **入力:** Related Need / Reporter Type / Outcome（必須）/ Story（必須）/ What Helped / What Did Not Help / What Is Still Needed。
- **誰が書くか（正直な階層）:**
  - **理想:** Recipient（本人）が書く。ただし戦災・難民では安全に得られないことがある。本人に書かせるために危険を冒さない。
  - **代理:** Gateway / Contributor / Observer が書く。これは一周を**閉じる**が、TTFR の厳密な「rescue」（本人 Positive/Mixed）には**満たない**ことを記録上明示する。
- **否定的・失敗も歓迎:** Negative/Failed を恐れず記録する。それが次の改善の唯一の材料。
- **記録される:** `reality_feedback_platform.jsonl`（`feedback_is_not_rating` 等）。

### Step 7 — 次の Voice へ繋ぐ（循環）
- **既存ページ:** `/feedback-paths`
- **動作:** Feedback の「What Is Still Needed」が **Potential New Voice 候補**として表示される（提案のみ・自動 Voice 化なし）。
- **意味:** 一周が終点ではなく、次の声の入口になる（D-8 の循環）。

---

## 6. 「一周 closed」の判定とTTFR

- **Loop closed の最小条件:** Step 1〜6 がすべて記録され、Step 6 に**少なくとも1件の Reality Feedback**（Recipient でなくとも可）が存在する。
- **TTFR achieved（厳密）:** Step 6 に **Recipient による Positive/Mixed** の Reality Feedback が存在する（既存 `ttfr_status` の定義どおり。Dashboard が自動判定）。
- **正直な区別:** 「Loop closed（代理 feedback）」と「TTFR achieved（本人 feedback）」を混同しない。最初の一件は前者で十分に意味がある。後者は安全に得られたときのみ。
- **確認方法:** 既存 `/dashboard`（TTFR / Voice Response Time / Feedback Outcomes は生カウント）。

---

## 7. 中止条件（いつ止めるか）

以下のいずれかで**直ちに中止**し、進行中の記録に中止理由を残す（append-only）:

- 当事者が撤回・拒否・沈黙した（撤回は失敗ではない。理由を問わない）。
- 同意が確認できないまま接触が必要になった。
- 接続が当事者を特定・危険化しうると判明した。
- 実在を偽らないと先に進めない状況になった（偽るくらいなら止める）。
- Gateway/仲介者が当事者の利益でなく自己利益で動いていると観測された（→ `/objection` に記録）。

> 中止は失敗ではない。**害を与えないことは、一周を完成させることより優先する。**

---

## 8. 異議と振り返り（既存機能で）

- **異議経路:** 当事者・関係者は `/objection` でいつでも異議を出せる（代理提出可・受理番号発行・状態追跡）。異議は当事者に不利に作用しない。
- **振り返り:** 一周後（または中止後）、Operator は `/feedback` に Observer として「設計上何が機能し／しなかったか」を記録する（人ではなく**仕組み**を評価。第5条: 失敗を当事者に帰属しない）。
- **学びの次への接続:** What Is Still Needed → `/feedback-paths` → 次の Voice。

## 10. このプロトコルの限界（隠さない）

- 本プロトコルは**最初の一件**のためのもの。スケール手順ではない。
- 戦災・難民の**個人**を Mujin が直接安全に一周させる確実な方法は、本プロトコルでも**未解決**である。だから個人ではなく「公開要請・既存チャネル経由」で扱う。これは困窮から逃げる迂回ではなく、**最も困窮に近い領域を安全に検証する形**だが、当事者個人にとっての Reach Gap が縮まったことは意味しない。
- 「困窮に近いケースを優先する」と決めても、安全ゲートを通れない最も困窮した声は今回の対象から外れる。**その外れた声こそが Reach Gap の中心**であり、本プロトコルはそれを解決しない——誰がそのコストを払っているかを記録し続ける。
- 代理 Reality Feedback で閉じた一周は、本人の経験を完全には捉えない。`lived_experience_is_not_authority` だが、**本人不在の一周は不完全**であることを記録に残す。
- 最大のボトルネックは依然として**人間**（Reviewer・Gateway 連絡担当・本人の同意）であり、これはバグではなく設計である。

---

*本プロトコルは運用手順であり、コード・新機能・新 ADR・新レイヤを含まない。目的は救済能力の誇示ではなく、最初の一人の経験を一件、安全に通すこと。一周が完成しても Reach Gap は未解決であり、本プロトコルもその解決を主張しない。*
