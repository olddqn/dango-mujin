## 0. なぜ分離会計が要石か

- TTFR-G（Gateway 救済）と TTFR-P（Person 救済）は**別母集団の別時計**。
- 危険: 単一の「TTFR」や「救済数」に合算すると、**gateway 支援の成功が person 未救済を覆い隠す**（F-7 の静かな失敗）。資金の付いた gateway を「救済」に数えれば、Reach Gap が縮んだ錯覚が生まれる。
- ∴ **分離会計が要石: TTFR-G を person 救済の代理にしない・Reach Gap から相殺しない・合算しない。**

```
TTFR-G  gateway 領域・gateway 自身の尺度・observable completion（F-16）
TTFR-P  person 領域・owner consent 要・現在 not started（封印・H-16）
Reach Gap  person 領域の条件・測らず観測縁で働く（F-8）
   ╳ 三者を合算・代理・相殺しない
```

## 1. Q1〜Q10 の監査

### Q1. TTFR-G とは何の時計か

**gateway の self-stated bottleneck が観測縁で観察されてから、gateway 自身の尺度で解消が observable になるまでの時間。** gateway 領域に閉じる。

### Q2. TTFR-G と TTFR-P は合算できるか

**No。** 別母集団（gateway / person）の別時計。合算は category error かつ person 未救済の隠蔽。

### Q3. TTFR-G completion は Reach Gap を縮めるか

**No（F-8/F-16）。** Reach Gap は person 領域の条件。gateway の bottleneck 解消は person を救っておらず、Reach Gap を 1 も縮めない。

### Q4. TTFR-G を person 救済の代理指標にできるか

**No。** 「gateway を助けた＝人を助けた」は代理の誤り。代理にすれば、容易な gateway 救済で困難な person 救済を粉飾できてしまう（Saiyan Scouter の会計版）。

### Q5. TTFR-G を最大化 KPI にできるか

**No（F-6 Q9）。** 最大化は選抜圧——支援しやすい gateway を選び、しにくい縁を捨てる。TTFR-G は記録するが最大化しない。

### Q6. TTFR-G completion は成功か

**gateway 領域の限定的成功であって、Dan-Go の使命達成でない。** 使命は person の Reach Gap 縮小（F-6/F-8）。gateway 成功を使命達成と読むのが F-7 の静かな失敗。

### Q7. TTFR-G と Reach Gap はどう併記するか

**対で・分離して。** TTFR-G（gateway 領域の進捗）と Reach Gap（person 領域のなお救われない者）を**並置するが混ぜない**——TTFR-G の前進が Reach Gap の存在を覆い隠さないため（F-6 Q7）。

### Q8. TTFR-G を gateway 間で比較できるか

**No。** gateway 間の TTFR-G 比較は gateway ranking（「速く救える gateway が良い」）＝Saiyan Scouter（F-6/H-11）。比較・順位付けしない。

### Q9. TTFR-G 会計に owner 情報は入るか

**No。** TTFR-G は gateway-as-actor の領域。owner の identity/need を会計に入れれば person domain 漏れ（F-9）。owner 非及。

### Q10. 最小正当 TTFR-G 会計は何か

**gateway 自身の尺度の observable completion を、TTFR-P・Reach Gap と分離して記録し、合算・代理・相殺・最大化・gateway 間比較・owner 混入をせず、使命達成と読まないもの。**
