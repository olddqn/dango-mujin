## 1. Q1〜Q10 の監査

### Q1. Gateway Bottleneck Support とは何か

**gateway が自ら公開した（self-stated public）operational bottleneck への、低介入・無表象・無ランキングの資源支援。**
- 対象は gateway-as-actor が**自分で「足りない」と公開したもの**（例: 自ら公表した資金不足・人手不足）であって、Mujin が推論した need でも、不在 owner の need でもない。

### Q2. Gateway Support は Gateway Representation か

**No（H1）。** bottleneck を支援することは、gateway を代弁することでも、gateway が Mujin を代弁することでもない。
- 資源が self-stated need へ流れるだけ。誰も誰かを代弁しない（Resource Acceptance ⊄ Representation・X-4.7）。

### Q3. Gateway Support は Gateway Participation か

**No（H2・核心）。** 支援を受領することは、gateway が Mujin の参加者・メンバー・ノードになることではない。
- gateway は**資源を受領した独立 actor のまま**——登録せず、Mujin の義務を負わず、Mujin 化しない（Resource Acceptance ⊄ Participation）。

### Q4. Resource Acceptance は Support を許可するか

**Yes（H3）。** gateway が self-stated need へ資源を受領すること（Resource Acceptance）が、gateway-domain support を正当化する consent。
- ただし**その層に限定**: 受領は資源の流れを許可するのみで、参加・代弁を許可しない。gateway の受領＝F-9 でいう gateway consent。

### Q5. Support は Contribution になるか

**支援者の act は無ランキングで記録されうるが、gateway を Mujin への contributor にしない。**
- 支援する側（資金・人手の出し手）の act は、**順位/評判帰属なし・human review 付き**で記録されうる（F-6/H-11）。
- だが (a) gateway は受領によって「Mujin に貢献」しない、(b) 縁は Contribution を自動生成しない。
- **支援は Resource Acceptance であって、attribution イベントでない。** contribution 機構（帰属→reputation）を起動しない。

### Q6. Support は Cooperation になるか

**単一 gateway の bottleneck 支援は Cooperation でない。consenting actor 間の調整は possibility-only（H-5）。**
- 複数の支援者/gateway が bottleneck を巡り調整するなら Cooperation——だが **possibility のみ記録・consent した当事者＋human が形成・Hermes は割当てない・actor は consent ある場合のみ名指し**。
- **支援は既定で Cooperation でない。** 協力は consent・possibility・無割当の範囲でのみ。

### Q7. Support は TTFR-G を完了させるか

**Yes——条件付き（H4）。** TTFR-G（Gateway 救済）は gateway の self-stated bottleneck が**実際に解消された時**に完了。gateway support はこれを直接進める。
- 重要な但し書き: 解消の尺度は **gateway 自身の self-stated need が満たされたか（gateway の基準）**であって、Mujin が「gateway は良くなった」と推論することではない。
- gateway-domain で止められる唯一の時計。

### Q8. Support は TTFR-P を始動させるか

**No（H4・最重要の honest 境界）。** gateway の bottleneck 解消は、person relief を始動・前進させない。
- 不在 owner は依然未救済（consent=0・person domain 封印）。**資金の付いた gateway ≠ 救われた人々。**
- **TTFR-G の前進を TTFR-P の前進と誤認してはならない。** JAR の資金を助けることは、JAR の背後の人々を救うことではない（評価フレーム TTFR-G vs TTFR-P）。誤認は「gateway relief を person relief と偽る」失敗。

### Q9. Support が Person Domain に漏れる地点はどこか

**4つの漏れ点:**
1. **条件化漏れ:** 支援を「owner への access」と引き換えにする（「資金を出すから clients を寄越せ」）。
2. **定義漏れ:** 「gateway の bottleneck ＝ owner の need」とすり替え、owner の need を定義する。
3. **proxy 漏れ:** 支援された gateway を Mujin の代理として owner へ行為させる。
4. **誤認漏れ:** TTFR-G 完了を TTFR-P（person 救済）として報告する（虚偽）。
- **漏れは、支援が gateway の self-stated public need を越え、不在の人々へ向かうあらゆる地点。**

### Q10. 最小正当 Gateway Support は何か

**self-stated public need への、低介入・無表象・無割当・無推薦の資源支援（Resource Acceptance 層・H5）。**
- gateway 自身の relief 尺度に従い、Participation/Representation/Selection/Attribution/Execution へ escalate せず、TTFR-G と TTFR-P を混同しない。
- **voice-006/JAR について:** JAR が**自ら公開した**資金・人手 bottleneck に資源で応える。JAR を Mujin 参加者にせず、JAR を代弁せず、JAR を他 gateway とランキングせず、JAR の不在 clients へ到達しない。

## 8. Reality Correction

```
voice-006 = Gateway Voice
Owner Consent = 0   Gateway self-stated need = present
Need = 0   Contribution = 0   Cooperation = 0
TTFR-P = not started   TTFR-G = possible
```

- voice-006 で **Person Relief は不可**（owner consent=0）。だが **Gateway Bottleneck Support は Resource Acceptance 層で正当に可能**——F-7 が名指した gateway 孤立への応答。
- **重大な honest 前提（Reality Correction）:** 支援は gateway の **genuinely self-stated・publicly stated な need と genuine consent** を前提とする。**JAR の bottleneck を Mujin が推測・捏造してはならない**（Jammy House/D.R.A. の教訓——未検証の org を実在の支援対象として誇張しない）。JAR が**実際に自ら公開した**ものにのみ応える。検証できない bottleneck への支援は、Reality Correction 違反。
- TTFR-G=possible は「JAR の self-stated bottleneck が解消されれば」であって、TTFR-P（person 救済）とは別。混同しない。
- honest 注記: Mujin raw の seed/test fixture は実在エンティティでない（一連と一貫）。実 Voice は voice-006 の 1 件。
