## 1. Q1〜Q10 の監査

### Q1. Observed Edge とは何か

**ギャップが推測なしに可視化される接触点。** voice-006 ＝ gateway が語った（観測）／背後の owner は不在（観測された不在、推測でない）。
- 縁は「ギャップが見える場所」であって、ギャップそのものでも、背後の人々でも、need でも、mandate でもない。**観察である。**

### Q2. Observed Edge は Need か

**No（H1）。** 縁は「ここに見える」という観察。owner の need を縁から読み取れば N-1.6 違反＝Saiyan Scouter。
- gateway は**自分自身の public need（自分の状況についての公開された need）**を持ちうるが、それは縁とは別物であり、不在 owner の need ではない。

### Q3. Observed Edge は Action を許可するか

**No（H2・それ自体では）。** 縁を観察したことは、行為してよいことを意味しない（is/ought・H-13）。
- 縁は「どこを見るか」を告げるが「行為してよい」を告げない。行為許可は各領域の条件（person＝owner consent、gateway＝gateway consent）から来る。

### Q4. Person Domain で何が禁止されるか

**owner consent ゼロゆえ、不在 owner への一切（H3・H-15/H-16）。** need 定義・代弁・solution 実行・接触・Contribution 帰属・Cooperation 巻き込み・代行決定。
- **Person Domain は封印（不可侵の床）。** voice-006 の owner consent=0 が続く限り、解けない。

### Q5. Gateway Domain で何が許可されるか

**gateway の self-stated public need の範囲で、gateway consent 付きに（H4）。**
- gateway は consenting actor。許可: **供給側調整・Bottleneck Support（Case D/E：協力者が互いを見つけられない／gateway が調整されない を助ける）**。
- 境界: **gateway 自身の公開された領域に限定。** gateway は自分について consent できるが、背後の人々については consent できない（H-15 Q4）。gateway 支援が person domain に漏れないこと（§5）。

### Q6. Findability Domain で何が許可されるか

**owner consent 不要で、受動的 Findability Improvement（H5・H-16/F-5）。**
- 許可: owner が**自ら Mujin を見つけ consent しうる門**を保つ/開く（F-1.7: 現状ほぼ発見不可）。
- 境界: **owner→Mujin の向きのみ・outreach に転じない・count を最大化しない**（F-5/F-6）。findability は誰にも到達しないゆえ consent 非依存。

### Q7. Observed Edge から Contribution は作れるか

**owner についての Contribution は No。gateway 自身の consenting act 由来なら gateway domain で条件付き可。**
- person domain（不在 owner への帰属）＝不可（封印）。
- gateway が participant として自ら寄与する act は gateway domain で成立しうる——ただし **gateway の能動 act ＋ human review** を要し、縁から自動生成されず、順位帰属もしない（F-6/H-11）。
- **縁は Contribution を“生成”しない。** consenting actor の act だけが、gateway domain に限り生む。

### Q8. Observed Edge から Cooperation は作れるか

**owner を巻き込む Cooperation は No。consenting gateway 間の供給側 Cooperation は possibility-only として、当事者＋human が形成。**
- person domain（不在 owner の巻き込み）＝不可。
- gateway-to-gateway / 供給側（Case D/E）の協力は、**H-5 の通り possibility のみ記録・Hermes は割当てず、consent した gateway たち＋human が形成**。
- **ここに正当な価値の中心がある**（供給側調整）——ただし Hermes は生成・割当しない。

### Q9. Observed Edge は TTFR を始動するか

**TTFR の時計を始動する（責任の開始）が、relief そのものではない。**
- 縁の出現（voice-006）＝「最初の救済までの時計」が動き始める時点。**責任は縁が観測された瞬間に始まる。**
- TTFR-G（Gateway 救済）は gateway domain support で**完了させうる**。TTFR-P（Person 救済）は owner consent 不在ゆえ**一時停止**（始動はしても person relief で止められない）。
- 現状 TTFR=undefined ＝ 縁で救済がまだ一件も realize されていない＝**動く時計が止まっていない**＝保留のコストが計上され続けている（F-7）。

### Q10. Observed Edge での最小正当行為は何か

**三つ:** ①**縁の観察記録**（Hermes memory・推測なし）②**Gateway を consenting actor として、その self-stated public need の範囲で支援**（Bottleneck Support・gateway consent 付き）③**Findability の維持/改善**（受動・owner が自ら来られる門）。
- **でないもの:** owner の need 定義・代弁・実行・選定・自動 Contribution/Cooperation 生成。
- **最小正当行為 ＝ honest な観察 ＋ gateway domain 支援 ＋ findability 改善。person domain には一切踏み込まない。**

## 4. 主要判定: voice-006 で可能なこと

**Person Relief ではなく、Gateway Bottleneck Support ＋ Findability Improvement。**

| 候補行為 | 領域 | 可否 | 根拠 |

## 5. 漏れリスク（許可領域が person domain を侵さないために）

1. **Gateway → Person 漏れ:** 「gateway を助ける」が「gateway の clients（不在 owner）へ到達する」に滑る。**封鎖: gateway consent の self-stated 範囲を超えない。owner へは到達しない。**
2. **Findability → Outreach 漏れ:** 「門を開く」が「人を集める/勧誘する」に滑る。**封鎖: owner→Mujin の向き・受動・count 最大化なし（F-5/F-6）。**
3. **Edge → Mandate 漏れ:** 縁の観察を「だから救え（owner へ）」に滑る。**封鎖: 縁は許可でない（Q3）・person domain は consent 待ち。**
