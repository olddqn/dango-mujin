## 中心問い

**最初の本物の Voice が Gateway（仲介者）から来たのは、偶然か、構造的必然か。**

先に観察からの暫定結論（§7 で根拠）: **構造的に「Gateway 起点が強く優遇される」。偶然ではない。** ただし n=1 であり、「必然」と断定はしない——安全ゲートの設計が Gateway 起点を**選びやすくする**ことは構造から言え、最初の1件がそれと整合した、という calibration に留める。

---

## 観察 1 — 最初の Voice は誰の声だったか（三主体の分離）

| 主体 | voice-006 における該当 | Voice 内に存在するか |
|---|---|---|
| **発信主体**（声を上げた者） | JAR（仲介者 NPO・Gateway 的主体） | ✅ 存在（声の主） |
| **Need 主体**（困りごとを抱える者） | 日本に逃れた難民（個人） | ❌ 不在（声の中に現れない） |
| **Contribution 主体**（声が向けられる相手） | 寄付者・ボランティア・協力者 | △ 想定された受け手として存在 |

**観察:** 発信主体と Need 主体が**分離している**。声を上げたのは Need を抱える本人ではなく、本人を支える仲介者。Need 主体は声の中で**代弁されてはいるが、発話してはいない**。

---

## 観察 2 — Gateway の役割（公開情報の範囲）

| 役割候補 | voice-006 / JAR の該当 |
|---|---|
| **Need の所有者** | ❌ 該当しない。JAR は難民の Need を「所有」しない。 |
| **Need の代弁者** | ◯ 部分的に該当。難民の状況を公開で語り、支援を呼びかける。 |
| **Need への接続者** | ◎ 主に該当。法的支援・生活支援・就労支援・コミュニティ支援へ難民を接続し、同時に支援者を難民へ接続する。 |

**観察:** Gateway は **接続者を主とし、代弁者を従とする**。所有者ではない。これは D-1 の Gateway 定義（「支援者ではなく接続者」）と一致する。voice-006 はその定義の最初の実例になった。

---

## 観察 3 — なぜ当事者 Voice が現れなかったのか

> **推測しない。** 公開情報からは「特定の個人がなぜ声を上げなかったか」は分からない。分かるのは、**安全ゲート（X-0 §3）がどの軸でふるいにかけているか**だけである。以下は個人の状況の主張ではなく、ゲートが課す**構造的フィルタ**の記述。

| ゲートが要求する条件 | それがふるい落とす軸（構造） |
|---|---|
| 公開出典がある | **公開発信能力**を持たない声は通らない（声を公開の場に出せること自体が前提） |
| 本人への直接接触なし | Mujin から個人へ届く経路を持たない声は、仲介者を介さない限り通らない |
| 失敗しても安全 | **安全性・法的地位**が脆弱で、声を上げること自体がリスクになる場合、本人発話は抑制される |
| （実務的に）言語・通信 | 公開要請を**言語・通信環境**の壁を越えて出せることが暗黙の前提 |

**観察:** これらは JAR が「法的支援・生活支援・言語/コミュニティ支援」を提供している事実と整合する——**そうした支援が要るということは、当事者が公開発信・言語・法的地位・安全の壁の手前にいることを意味する**。当事者 Voice が現れなかったのは、ゲートがまさにその壁の外側でしか声を拾えないからである（個人の事情の推測ではなく、ゲート設計の帰結）。

## 観察 4 — Reach Gap の位置

現在の仮説:
```
困窮者 → Gateway → Mujin
```

観察に基づく修正:
```
困窮者 ──(gap-1: 個人 → 仲介者)──▶ Gateway ──(gap-2: 仲介者 → Mujin)──▶ Mujin
                                                  ▲ voice-006 はこの gap-2 を初めて橋渡しした
```

- **Mujin が橋渡ししたのは gap-2（仲介者 ↔ Mujin）** であって、gap-1（個人 ↔ 仲介者）ではない。
- gap-1（難民個人が JAR に到達できているか）は **Mujin の外で起きており、voice-006 からは観察できない**。JAR に到達できていない難民は、gap-1 の手前に残る。
- **Reach Gap は単層ではなく少なくとも二層。** Mujin が触れたのは外側の層（gap-2）。最も困窮した個人は gap-1 の奥にいて、今回の一周では一切触れられていない。
- 仮説「困窮者 → Gateway → Mujin」は、**矢印が一本に見えて実は二段の到達問題を畳んでいた**。voice-006 はその畳みを開いて見せた。

## 観察 5 — TTFR への示唆

最初の Voice が Gateway Voice だった場合、そこを起点に測る TTFR は何を測るか:

| 測っているもの | 該当 |
|---|---|
| **困窮者が助かった時間** | ❌ 直接は測れない。Need 主体（難民個人）は声の中に不在で、その人が助かったかは voice-006 起点では観測されない。 |
| **Gateway が支援を受けた時間** | ◯ これを測ることになる。仲介者が資源（寄付・人手）を受け取るまでの時間。 |

**観察（重要）:** voice-006 を起点に「rescue」を測ると、それは **「Gateway が支援を受けた時間」** であって「困窮者が助かった時間」ではない。プラットフォームの `ttfr_status` は Recipient（受け取った本人）の Positive/Mixed を rescue とするが、**Gateway Voice の Recipient は Gateway であって個人ではない**。ここに**測定のカテゴリ錯誤の危険**がある: 仲介者支援を個人救済と取り違えうる。区別が必要——記録する（新機能は提案しない）。

---

## 観察 6 — Mujin への示唆（結論を固定しない）

「Mujin が最初に扱うのは何か」を、最初の実データ1件から観察する:

| 候補 | 最初の一件（voice-006）の実際 |
|---|---|
| Need（個人の困りごと） | ❌ 直接は扱っていない。Need 主体は不在。 |
| **Bottleneck（資源の目詰まり）** | ◎ 実際に扱ったのはこれ。「支えるための資源が足りない」（資金・人手）。 |
| **Gateway Voice（仲介者の声）** | ◎ 入口として扱ったのはこれ。 |

**観察:** 経験的に、Mujin が最初に実際に扱ったのは **Gateway Voice が表す Bottleneck** であり、個人の Need ではなかった。

これが意味しうること（**結論を固定せず両論を記録**）:
- **解釈A（構造）:** Mujin は本質的に、到達可能な仲介層の Bottleneck を解く「目詰まり解消プラットフォーム」であり、個人 Need は仲介層の奥にある——Mujin が直接触れない層かもしれない。
- **解釈B（人工物）:** これは最初のケース選定（安全ゲート優先）の産物にすぎず、当事者 Voice を狙えば個人 Need を直接扱える可能性が残る——ただし当事者 Voice は安全ゲートを通りにくい（観察3）。
- どちらが正しいかは n=1 では決まらない。**次の数件の実 Voice が当事者か仲介者かを観察すれば、解釈A/B のどちらに寄るかが見えてくる。**

## 学習事項（列挙）

1. **発信主体と Need 主体が分離していた。** 声を上げたのは仲介者、Need を抱えるのは不在の個人（観察1）。
2. **Gateway は接続者であり、Need の所有者ではない。** voice-006 は D-1 の Gateway 定義の最初の実例（観察2）。
3. **当事者 Voice が現れなかったのは、安全ゲートが公開発信能力・直接接触不可・安全性・言語/通信の軸でふるいにかけるから。** 個人の事情の推測ではなく、ゲート設計の帰結（観察3）。
4. **Reach Gap は二層。** Mujin が橋渡ししたのは gap-2（仲介者↔Mujin）。gap-1（個人↔仲介者）は Mujin の外に残り未観測（観察4）。
5. **Gateway Voice 起点の TTFR は「Gateway が支援を受けた時間」であり「困窮者が助かった時間」ではない。** 測定のカテゴリ錯誤に注意（観察5）。
6. **Mujin が最初に実際に扱ったのは個人 Need ではなく、Gateway Voice が表す Bottleneck だった**（観察6）。
7. **中心問いへの暫定回答: 構造的に Gateway 起点が優遇される（偶然ではない）。ただし n=1 で「必然」とは断定しない。** 安全ゲートが原因（§中心問い・観察3）。
8. **gap-1 を観察する手段を Mujin は現在持たない**（個人↔仲介者の到達は仲介者の内部で起き、Mujin の外）——これは欠落だが、本レビューは新機能を提案しない。観察として記録。

## 次フェーズ判断のための論点（X-3 前に人間が決めること）

- voice-006 から Need Candidate を作るなら、それは **Gateway の Bottleneck（資源要求）への協力候補**であって、**個人 Need の充足候補ではない**。両者を混同しないこと（観察1, 5, 6）。
- 「最初の数件を意図的に当事者 Voice／仲介者 Voice で振り分けて観察する」ことが、解釈A/B の判別材料になる（観察6）——ただしこれは選定方針の問題であり、本レビューは決定しない。
- TTFR ダッシュボードの「rescue」が Gateway 支援を個人救済と取り違えないよう、**この一件は『Gateway が支援を受けうる経路の最初の接続』として記録し、個人救済の TTFR としては数えない**ことを推奨（観察5。ただし最終判断は人間）。
