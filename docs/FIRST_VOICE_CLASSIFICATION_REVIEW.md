## 1. Voice の種類

> 設問: voice-006 は A〜D のどれに該当するか（複数可）。

| 型 | 内容 | voice-006 の該当 |
|---|---|---|
| **A. 当事者 Voice**「助けてくれ」 | 困っている本人の直接の声 | **該当しない。** voice-006 は難民個人の声ではなく、難民を支援する**組織**の公開要請。 |
| **B. 仲介者 Voice**「助けるための資源が足りない」 | 支援を担う者が、支援を続けるための資源を求める声 | **主に該当。** JAR は運営資金の約7割を民間寄付に依拠し、公開ページで寄付・ボランティア（One Action for Refugees 等）を募っている。「難民を支えるための資源（資金・人手）を求める声」。 |
| **C. 構造 Voice**「仕組みが機能していない」 | 制度・構造の不全を指す声 | **部分的に該当。** 「日本に逃れた難民が安心して暮らし、ともに生きられる社会を目指す」という枠組みは、既存制度だけでは難民の法的・生活・就労・コミュニティの必要が満たされていない構造を背景に持つ。ただし voice-006 自体が構造批判として発せられているわけではない。 |
| **D. 解決 Voice**「こうすれば解決できる」 | 解決手段の提案 | **弱く該当。** 「法的支援・生活支援・就労支援・コミュニティ支援」という活動形は緩やかな解決アプローチだが、特定の解決機構の提案ではない。 |

**観察結果:** voice-006 は **B（仲介者 Voice）を主とし、C（構造）を背景に持つ**。A（当事者の直接の叫び）ではない。

## 2. Voice と Need の関係

- voice-006 は**直接 Need を表していない**。「特定の誰かが何を必要としているか」ではない。
- voice-006 は、**Need を抱える人々（日本に逃れた難民）への仲介要求**である: 「彼らを支えるための資源（寄付・ボランティア）を提供してほしい」。
- 構造で言えば:

```
難民（個人）── Need を抱える（言語・法的・生活・就労）
      ▲ 仲介
   JAR（組織）── voice-006 =「支えるための資源が足りない」
      ▲ 資源要求（公開）
   寄付者・ボランティア・協力者
```

- つまり Need の**所有者は難民個人**であり、voice-006 は**その Need に至る仲介層からの資源要求**である。Need 本体は voice-006 の中には無い。

公開ページから読み取れる、JAR が示すボトルネック:

## 4. Dan-Go / Mujin への示唆

> 設問が示した観察: **「最初の本物の Voice は、当事者の叫びではなく、仲介者の叫びだった。」**

この事実が意味することを、推測せず構造として考察する。

### 4.1 これは偶然ではなく、安全ゲートの構造的帰結である
X-0 §3 の安全ゲート（本人への直接接触なし・公開出典あり・失敗時安全）は、**当事者個人の直接の叫び（A）を構造的にふるい落とし、仲介者の公開要請（B）を通す**。最初の Voice が B だったのは選定の偶然ではなく、**ゲートの設計がそうさせた**。困窮の中心にいる個人ほど、公開の声を安全に上げられない——だから最初に届くのは、その人々を代弁する仲介者になる。

### 4.2 仲介者層（Gateway）は「到達可能な層」である
これは D-1 の Gateway 概念の実証でもある:「Agent は能力を増やすが、Gateway だけが Reach Gap を縮める」。仲介者は、当事者個人と Mujin の間の**到達可能な接点**として機能する。voice-006 は、その到達可能層からの最初の声だった。

### 4.3 しかし Reach Gap は縮んでいない
仲介者に届いても、**仲介者の背後にいる、仲介者にも届いていない個人**は依然として Reach Gap の中にいる。voice-006 が示すのは「到達可能な仲介層の存在」であって、「個人への到達」ではない。最初の Voice が仲介者だったことは、**Mujin が到達できる層と、できない層の境界線を可視化した**。

### 4.4 TTFR は代理測定になる（正直な限界）
voice-006 を起点に一周しても、Reality Feedback は JAR（仲介者）または観察者からのものになり、**難民個人本人の Positive/Mixed**（X-0 §6 の厳密な TTFR）には届きにくい。Loop closed（代理 feedback）と TTFR achieved（本人 feedback）の区別が、最初の実ケースから既に現れている。

### 4.5 設計上の含意 — Voice 分類は data model に無い（追加しない）
Mujin の入口は当初「Voice =『助けてくれ』（当事者）」を想定していた。だが現実の最初の Voice は B（仲介者）だった。Voice Submission + Gateway の仕組みは B を扱えるが、**A/B/C/D の区別はデータモデルに存在しない**（全 Voice が `voice_category` の一語に潰れる。voice-006 は `Other`）。これは設計の欠落かもしれないが、**本レビューは新機能を提案しない**——観察として記録するに留める。仲介者 Voice と当事者 Voice を同じ変換で扱うと、Need Candidate の意味（誰の Need か）が曖昧になりうる。

### 4.6 Voice と Contribution の境界の曖昧化
B（仲介者 Voice）「資源が足りない」は、見方を変えれば「組織への Contribution の Need」でもある。D-6 で分けた「助けてくれ（Voice）」と「助けたい（Contribution）」の境界は、仲介者層では曖昧になる。voice-006 はその曖昧さを最初の実ケースで露呈させた。

## 5. 学習事項（列挙）

1. **最初の実在 Voice は当事者（A）ではなく仲介者（B）だった。** これは安全ゲートの構造的帰結であり、偶然ではない（§4.1）。
2. **困窮の中心にいる個人ほど、公開の声を安全に上げられない。** 最初に届くのは代弁する仲介者になる（§4.1）。
3. **voice-006 は Need を直接表さない。** Need の所有者は難民個人であり、voice-006 は仲介層からの資源要求である（§2）。
4. **読み取れるボトルネックは資金不足・人材不足**（公開明示）。法的/生活/就労/言語は活動分野として示されるが需要規模は不明（§3）。
5. **仲介者層は到達可能層だが、その背後の個人は Reach Gap のまま**（§4.3）。
6. **TTFR は代理測定になりやすい。** Loop closed と TTFR achieved の区別が最初から必要（§4.4）。
7. **A/B/C/D の Voice 区別はデータモデルに無く、変換時に「誰の Need か」が曖昧になりうる**（§4.5）。新機能は提案しない、観察として記録。
8. **仲介者 Voice では Voice（助けてくれ）と Contribution（助けたい）の境界が曖昧になる**（§4.6）。

## 6. 次フェーズ判断のための論点（X-3 に進む前に人間が決めること）

- voice-006 を Need Candidate に変換することは、「**JAR の活動への協力可能性**」を談合材料にすることであり、「特定の難民個人の Need」を作ることではない。この区別を明示してから進むべき（§2, §4.5）。
- 変換するなら、suggested_need_type は組織活動の文脈（翻訳・法的・生活支援への協力）として解釈し、**当事者個人の Need と混同しない**。
- あるいは、最初の一件は「当事者 Voice（A）」を別途探す方が設計意図に近いかを問う——ただし A は安全ゲートを通りにくい（§4.1）。このジレンマ自体が記録すべき学習。
