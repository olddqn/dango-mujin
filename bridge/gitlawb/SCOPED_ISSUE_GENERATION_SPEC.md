# Scoped Issue Generation Spec

**A scoped issue is not a command. It is a negotiation invitation.**

This document specifies how the Dan-Go scoped prerequisite pipeline
translates OGI plan tree output into Gitlawb issue drafts.

No real issue is created. No API is called. No authority is asserted.

---

## 1. Why Scope Matters More Than Universal Rule Generation

A federation prerequisite is a convergence signal. It arose because
multiple independent claims discovered the same condition as necessary.
It is not a law. It is not a requirement issued by a coordinator.

But not every claim is in the same context.

A prerequisite scoped to `non_precertified_spaces` does not apply to
a precertified building. Generating an issue draft anyway would be:
- meaningless for the resolving agent
- insulting to the claim author
- a false signal in the negotiation record

**Scope determines whether a prerequisite generates an issue or remains
silent. Universal issue generation is wrong.**

---

## 2. Why an Applicable Prerequisite Creates an Issue Draft

When `compute_inheritance(claim_id)` returns a condition in
`applicable_prerequisites`, the OGI plan tree includes it as a subgoal.
The claim is structured around satisfying this condition.

An issue draft is generated to:
- surface the condition to human/agent reviewers
- invite evidence submission via PR
- record the advisory gap in the negotiation layer

The issue draft is:
- `issue_candidate: true`
- `advisory: true`
- `execution_allowed: false`
- `moves_money: false`
- `contestable: true`
- `negotiation_reopen_allowed: true`

**The issue invites resolution. It does not demand it.**

---

## 3. Why a Bypassed Prerequisite Suppresses Issue Creation

When `compute_inheritance(claim_id)` returns a condition in
`bypassed_prerequisites`, the OGI plan tree includes it as an audit
assertion — not a subgoal. The plan tree records _why_ the bypass
was recognised.

No issue draft is generated because:
- the condition is not a local requirement for this claim
- an issue would create false pressure to satisfy a non-applicable rule
- the bypass is already recorded in the plan tree as memory

A suppression record is created instead:
- `issue_candidate: false`
- `reason: "prerequisite bypassed by scoped resolution"`
- `scope_status: "bypassed"`
- `bypass_conditions_found: [...]`

**A bypassed prerequisite is still memory. It is just not an active
requirement in this context.**

---

## 4. Why Issues Remain Advisory

No issue in this pipeline has `execution_allowed: true`.
No issue triggers automatic plan changes.
No issue assigns authority.

An issue is a structured negotiation invitation — it says:
> "The plan tree suggests this condition matters here. Here is the evidence
> that would resolve it. Do you agree?"

The response can be:
- a PR with evidence (issue advances)
- a contest via better plan tree (issue lapses)
- silence (issue remains open as a reminder)

Any of these is a valid outcome. The protocol does not enforce resolution.

---

## 5. Why Negotiation Can Reopen After PR Merge

`negotiation_reopen_allowed: true` is set on every record — before, during,
and after a PR merge event.

PR merge is not truth. It records that evidence was accepted at a point in
time by the reviewers present. It does not:
- permanently close the negotiation
- prevent a better plan tree from superseding the condition
- prevent the claim author from contesting the prerequisite scope

After merge, a `plan_correction` event by the plan author is needed to
formally update the plan tree. Until then, the plan tree does not change.

**PR merge + plan_correction = condition satisfied in the plan.
PR merge alone = evidence accepted, negotiation can still reopen.**

---

## 6. Why PR Merge Is Not Truth

The Dan-Go protocol is append-only. Plans grow by new events, not by
overwriting old ones. A PR merge is a signal in the event log — it records
that reviewers accepted the evidence at a given timestamp.

But the plan tree is generated by reasoning over all events in sequence.
If a later event (plan_correction, contest, new claim) changes the
interpretation, the plan tree is updated accordingly.

**The su-table is truth. PR events are inputs to the su-table.**

A merge without a `plan_correction` event is an orphaned signal: real,
recorded, but not yet integrated into the plan tree reasoning surface.

## 7. Filter Rules

`scoped_issue_filter.py` applies the following filters in order:

| Rule                  | Action     | Reason                                      |
|-----------------------|------------|---------------------------------------------|
| `scope_status=bypassed` | suppress | prerequisite does not apply to this claim  |
| `prerequisite_state=deprecated` | suppress | lifecycle ended — no longer relevant |
| duplicate condition (same claim_id) | dedup | keep first applicable, discard rest |
| `prerequisite_state=weakened` | annotate | add scope note; issue draft still created  |

Suppressed records are not discarded. They are returned as
`issue_candidate: false` with `filter_action` and `filter_reason` fields.

## 9. Negotiation Context Block

Every issue draft produced by `scoped_plan_to_issue.py` includes:

```json
"negotiation_context": {
  "contestable": true,
  "authority": "none",
  "hard_enforcement": false,
  "negotiation_reopen_allowed": true
}
```

`contestable: true` means: if you believe this prerequisite does not apply
here, you can contest it by producing a better plan tree. No coordinator.
No adjudicator. Better evidence wins.

## 10. Pipeline Summary

```
OGI Scoped Plan Tree (scoped-plan-*.output.json)
  │
  ├── issues_from_scoped_tree()    [scoped_plan_to_issue.py]
  │     applicable → issue_candidate: true
  │     bypassed   → issue_candidate: false
  │
  ├── _apply_filters()             [scoped_issue_filter.py]
  │     deprecated → suppress
  │     bypass     → suppress
  │     weakened   → annotate
  │
  ├── scoped_issue_to_task()       [scoped_issue_to_task.py]
  │     issue_candidate: true  → agent task (execution_allowed: false)
  │     issue_candidate: false → suppression record
  │
  ├── generate_scoped_pr_feedback() [scoped_pr_feedback.py]
  │     pr_opened   → condition_evidence_submitted
  │     pr_reviewed → condition_evidence_reviewed
  │     pr_merged   → condition_evidence_accepted
  │                   (negotiation_reopen_allowed: true always)
  │
  └── build_snapshot()             [scoped_issue_snapshot.py]
        Full view across all claims + conditions
```

## 11. Absolute Prohibitions

- No real issue is created
- No GitHub API or Gitlawb API is called
- No real PR is created
- No network access
- No token, wallet, or funds
- No external libraries (stdlib only)
- No hidden scoring
- No hard enforcement — `hard_enforcement: false` always
- No auto-execution — `execution_allowed: false` always
- `moves_money: false` always
